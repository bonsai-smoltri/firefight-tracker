# AGENTS.md

## Project Overview

Firefight Tracker — a mobile-first PWA for Grimdark Future: Firefight (OPR, v3.6). Import two Army
Forge lists, pick attacker, weapon and target, and see the final roll numbers with every
stat-changing rule applied. Tracks the battle, and rolls dice only when Roll is pressed.

The full plan is in `~/dev/home-projects/onepagerules/PLAN.md`. Sibling project `hammer-math` (40k)
is the template for stack, layout and mobile conventions.

## Tech Stack

- Preact (hooks), Vite, TypeScript
- Tailwind CSS 4 + DaisyUI 5
- vite-plugin-pwa
- vitest
- No backend; state is client-side

## Data

Army Forge has no documented API. The app uses the endpoints Army Forge itself calls, which can
change without notice:

| Data | Endpoint | Used by |
|---|---|---|
| Core rules | `/api/rules/common/3` | sync script |
| Official book index | `/api/army-books?filters=official&gameSystemSlug=gff` | sync script |
| Army book | `/api/army-books/{uid}?gameSystem=gff` (no CORS) | sync script |
| Shared list | `/api/tts?id={shareId}` (CORS `*`) | app, at import |

`src/data/` is generated by `npm run sync` and committed. Don't hand-edit it.

- `core-rules.json`, `books/{uid}.json` — trimmed to rules and spells.
- `manifest.json` — book versions and a hash of every rule description.
- `rule-index.json` — rule id to name and alias, used to resolve aliases.
- `sync-report.md` — mapped rules with unreviewed text, what changed since the last sync, and
  unmapped rules that look stat-changing. `mapping.test.ts` fails when a core rule's text
  changes or a reviewed hash no longer matches any text.

Rule ids are global across books (one id per rule name), so mappings key on id.

## Architecture

```
scripts/
  sync-army-forge.ts   # entry point for npm run sync
  sync/                # pure fetch/trim, manifest diff and report logic, with tests
src/
  app.tsx              # root; holds both players' lists
  data/                # generated
  types/
    army-book.ts       # bundled data shapes, shared by app and scripts
    list.ts            # ParsedList / ParsedUnit / ParsedWeapon
  lib/
    army-forge/
      tts.ts           # parses /api/tts JSON into a ParsedList
      import.ts        # share link or export file -> fetch -> parse
      fixtures/        # real lists (product/base data stripped) for tests
    storage.ts         # localStorage, validated on read
  components/
    ListSlot.tsx       # import by link or export file, list preview
    UnitSummary.tsx    # one unit's stats, weapons and rules
    AttackScreen.tsx   # attacker/target/weapon pickers, situation toggles, readout, Roll
    AttackReadout.tsx  # final roll numbers as plain lines, plus the expected wounds
    RollResult.tsx     # each rolled step with its dice
    RulesInPlay.tsx    # every rule's status for this attack, with its text
    Stepper.tsx        # touch-sized +/- count, copied from hammer-math
    BattleSetup.tsx    # first player, objective count, Aura recipients
    BattleScreen.tsx   # unit rows, activation panel, end of round, result
    MoraleDialog.tsx   # Quality test with Passed/Failed and an optional Roll
    BattleLog.tsx      # log grouped by round, shared by live and archived battles
    HistoryList.tsx    # past battles on the home screen
  lib/
    battle.ts          # battle state transitions
```

Screens are switched by a `view` state in `app.tsx`; there is no router: home, calculator, battle
setup, battle, battle attack (the attack screen with a `battle` prop) and a history record. A battle
under way is resumed straight into the battle screen on load.

### Battle tracking

All battle rules live in `lib/battle.ts` as pure `BattleState -> BattleState` functions, tested in
`battle.test.ts`. Components only call them.

- Units are keyed `${player}:${selectionId}`, because selection ids are only unique per list.
- Wounds are one total per unit, filled one model at a time against Tough. `modelsLeft` and
  `atHalfOrLess` derive from it (single-model units use their Tough).
- Activation flow: `startActivation` → `recordAttack` (any number, including a strike back) →
  `endActivation`, which queues morale tests in `pendingMorale`. The activation only finishes once
  every test is resolved with `resolveMorale`. Shaken units fail automatically.
- Melee: the first melee attack by a charging unit opens `activation.melee`. The loser is whoever
  took more wounds this activation, counting the other side's Fear. Units in that melee don't take
  the wounds test.
- `endRound` only runs once every unit has activated. It clears Fatigue, adds spell tokens (max 6),
  and gives first activation to whoever finished first. After round 4 it marks the battle complete.
- Auras are assigned at setup (`AuraAssignment`) and reach the engine through `grantedByAuras`
  while the holder is on the table. Buffs and Marks are per-attack toggles on the attack screen
  (`grantOptions`). Debuffs aren't offered, because their base rule reads the opposite way.
- `archiveBattle` in `app.tsx` is the only place a battle leaves the active slot. Changing a list
  ends the battle, since it refers to the lists' units. The attack screen only
shows situation toggles that some rule in play cares about (`attackControls`), plus Cover for
shooting and Charging/Fatigued for melee. Dice are rolled by `lib/rules/dice.ts` from the same
`ResolvedAttack` the readout shows, and only when Roll is pressed; a roll is hidden as soon as any
input changes.

### Rules engine

All game logic lives in `src/lib/rules`, with no UI imports. Files there use `.ts` import
extensions because the sync script imports them under Node.

- `types/rules.ts` — `RuleMapping` = one or more `RulePart`s, each held by the attacker or the
  defender, with conditions (mode, situation toggles, target Defense range) and effects. Effects
  are from the attack's point of view: Stealth is a negative `hitModifier` on the defender side.
- `mapping.ts` — every reviewed rule, keyed by **name** (the same rule has different ids in
  different books). Rules that change no numbers are `textOnly`, so they count as reviewed.
  `reviewed` holds hashes (`hash.ts`, FNV-1a) of the texts the mapping was checked against.
- `resolve.ts` — mapping by name, then the declared alias (`rule-index.json`), then wrappers:
  `X in Melee` / `X when Shooting` add a mode, `X Aura` applies X to its holder, and
  `X Buff` / `Debuff` / `Mark` do nothing for the holder (they're given to other units).
- `engine.ts` — `resolveAttack(input)` returns the final roll numbers, a report of every rule's
  status, and expected hits and wounds. A rule counts once per side however many sources give it.
  `enhances` makes an Enhanced rule replace its base rule. A mapped rule whose text in the list
  hasn't been reviewed is reported as `unreviewed` and kept out of the maths.

Adding a rule: add it to `mapping.ts` with the hash from `sync-report.md`, and a test in
`engine.test.ts` if it introduces a new effect or condition. Every Firefight rule is currently
mapped (stat or text-only) except Precision Debuff, so anything new in the report has just
appeared in a sync.

Mapping shapes beyond a plain part:
- `atRange(side, effects)` covers "shooting/charging from over 9"/6" away" as two parts.
- `manual: 'label'` makes a part a named toggle (`Rule: label`). `choice()` uses it for rules
  where the player picks or rolls an effect (Unpredictable, Versatile Expert) and for token counts
  (Piercing Growth).
- `armyWide` is for markers any friendly unit uses against a marked enemy (Precision Target, Tags,
  Spotters, Vengeance). They only apply when toggled under Buffs and Marks, never just because the
  attacker holds the rule.
- `synthetic` names a base rule that doesn't exist on its own, only through wrappers
  (`Precision Shooter` for Precision Shooter Aura and Buff). `reviewed` then holds the wrappers'
  text hashes.
- Situations that are usually true start on (`targetAboveHalf`). In a battle, the attack screen
  fills target situations in from battle state.
- Attacks in this app are never spells, so "not from spells" rules (Shielded, Spell Resistance)
  always apply.

Hazards:
- Bane, Rending and Unstoppable ignore **Regeneration** only. Self-Repair and Protected are
  different rules and still apply.
- Fatigued melee hits only on unmodified 6s, and those 6s trigger no special rules.
- Blast is capped at the models in the target using the full hit distribution, not the mean.

### List import

- The share link is the only source of resolved list data. An Army Forge export file only holds
  unit and upgrade ids, so the app reads its `id` and fetches the same `/api/tts` endpoint.
- Use the list's `loadout` (final weapons and upgrade items), not `weapons`. Rules granted by
  upgrade items are merged into the unit's rules.
- Unit points are `cost` plus the selected upgrades' costs.
- Some rule refs arrive with no id and are missing from the list's rule table (e.g. Deadly,
  Reliable). They are filled in from the bundled core rules by name.
- Unknown share ids return a 500, not a 404.
- `name` is the unit type; `customName` is what the player called it.

## Conventions

- Functional Preact components with hooks; DaisyUI classes for UI, Tailwind for layout.
- Types in `src/types/`, imported as `type` imports.
- Tests live next to the code as `*.test.ts`. List parsing is tested against the real lists in
  `lib/army-forge/fixtures`; everything else uses inline fixtures.
- 2-space indent, single quotes, no semicolons.
- Scripts run on Node's built-in TypeScript support, so they must use erasable syntax only and `.ts`
  import extensions.
- Every count control is a +/- stepper, and touch targets are at least 36px (44px full-width), as
  in hammer-math.

## Commands

- `npm run dev` — dev server on port 4202
- `npm run build` — type-check and production build
- `npm test` — run tests once
- `npm run sync` — refresh `src/data` from Army Forge (56 requests, 0.5s apart)
- `npm run sync -- --offline` — rebuild the index, manifest and report from `src/data`, e.g.
  after changing `mapping.ts`
